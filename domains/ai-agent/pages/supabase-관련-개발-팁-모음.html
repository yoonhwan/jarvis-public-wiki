Supabase 관련 개발 팁 모음

Threads @dalgom.bami — Supabase를 실제로 쓰며 정리한 비용·보안·운영 꿀팁 12선

본문 (Main Post)

비용 / 무료 플랜 활용

  1. MAU 5만까지 Free — MVP·PMF 찾기 전까지 DB 비용을 아낄 수 있어 최고.
  2. Storage는 1GB까지 무료 — 보통 이걸 초과해 유료 결제하게 되는 포인트. 굳이 쓸 필요 없이 Cloudflare R2를 쓰면 월 10GB 무료.

구글 로그인 / 도메인

  1. 구글 로그인 연동이 쉽다. 단, 연동 시 {랜덤문자}.supabase.co 같은 도메인이 로그인 화면에 노출돼 이상한 사이트처럼 보임. 이걸 해결하려고 $10짜리 커스텀 도메인을 결제하는 사람들이 있는데 그럴 필요 없다. GCP OAuth → Branding에서 verification만 제대로 하면 이상한 URL 대신 아이콘 + 서비스 이름으로 노출 가능.
  2. 커스텀 도메인(+$10/월) 은 주소창에 순간적으로 뜨는 리다이렉트 주소까지 거슬릴 때만 하는 것.

백업 / 마이그레이션

  1. Free는 자동 백업 안 됨 — 직접 dump를 떠야 함. 보통 이것 때문에 Pro 플랜을 시작함. Pro는 하루 1번, 최근 7일간 DB 데이터를 저장/복구 가능. 서버 지식이 없는 바이브코더라면 이거라도 해두자 — 개발자가 날아간 DB를 살려줄 수 있다.
  2. 추후 다른 DB로 마이그레이션 계획이 있다면 RLS로 클라이언트↔Supabase 직접 연결 로직을 쓰면 나중에 엄청 고통받는다. 그냥 wrapping하는 서버를 띄우고 service role로 권한 체크하는 전통적인 백엔드 방식으로 하면 추후 스무스하게 마이그레이션 가능.
  3. 로컬 Supabase를 개발 DB로 사용하고, DB 스키마 변경은 무조건 migration 파일을 생성해 로컬에서 반영·테스트 → 운영(또는 스테이징)에 supabase client로 migration 반영. 웹 대시보드에서 테이블 구조를 막 바꾸면 안 됨.

트랜잭션 / 운영

  1. 트랜잭션이 필요하면 RPC를 써야 하는데, 파일이 아닌 DB에 로직이 저장되다 보니 유지보수가 힘듦. 트랜잭션이 특히 중요한 애플리케이션이면 전통적인 Server↔DB client 구조 권장.
  2. 무료 플랜은 1주일간 트래픽 없으면 일시정지됨. 꾸준히 직접 들어가거나 cron으로 호출해서 해결 (단, cron 자동 정기 호출은 정책 위반).
  3. 보안 — 제대로 알고 쓰면 보안 이슈 거의 없음. 좋은 백엔드 스택을 가져와도 쓰는 사람이 모르면 허점이 생김. 단, Supabase는 권장 사용 방식대로 쓰다 보면 보안적으로 실수하기 좋은 구조임.
  4. queue, cron도 Supabase plugin으로 바로 쓸 수 있지만 유지보수가 지옥 — 비추.
  5. 로컬에 세팅해두고 쓰는 Supabase DB 테스트가 진짜 사기(꿀)임.
추후 Supabase 도입 계획이 있다면 저장해두고 나중에 보세요!

Q. (브랜치) 2개까지밖에 안 되는 건 어떻게 해결하시나요?

A (작성자). 보통 회사 이메일 계정으로 시작했다가 Pro 플랜을 씀. 무료로 여러 프로젝트를 계속 하려면 다계정밖에 답이 없을 듯.

C. 8번 진짜 공감 — 클라이언트 사이드 페칭 first 철학을 고수하는데, 트랜잭션이랑 raw SQL 쿼리는 좀 열어줬으면. 제발!!

백번 양보해 클라이언트 커넥션 트랜잭션은 그렇다 쳐도 edge function에서는 돼야 하는 거 아닌가. edge function은 Deno 환경이라 잘 안 쓰게 됨 — 장점이 없음.
C. Deno는 진짜 최악의 수, 왜 아직도 번복 안 하는지 이해가 안 됨.
