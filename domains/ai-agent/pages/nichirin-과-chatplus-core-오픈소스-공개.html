핵심 요약

개인 프로젝트 "헤임달"의 메신저 통합 도구 4종이 전부 오픈소스로 공개 완료. 카카오톡/채팅+(SK텔레콤)/텔레그램/디스코드/슬랙을 로컬에서 읽고·추적하고·보내는 CLI + 웹 클라이언트 + 어댑터 모음 구조.

⚠️ 중요 — 비공식 도구 / 계정 제한 위험

  • 카카오/SK텔레콤과 무관한 개인(비공식) 도구다. 공식 API가 아니라 로컬에 저장된 데이터를 직접 읽고, 로그인된 클라이언트 창을 대신 조작해서 보낸다.
  • 이 방식 때문에 각 서비스 약관상 계정이 일시/영구 제한될 수 있음 — 책임은 전부 사용 당사자. 각 저장소 상단 + DISCLAIMER.md에 명시.

저장소별 핵심 상세 (README 기반 보강)

nichirin (github.com/sanguneo/nichirin)

  • Windows(kanao, Python 3.10+) / macOS(kamado, Python 3.9+) 빌드를 하나의 리포로 통합 (#77, 구 kanao-cli+kamado-cli 병합)
  • 의존성 0개 — Python 표준 라이브러리 + OS API만 사용. 읽기는 네트워크 접근 없이 전부 로컬.
  • 기능: status/context --room/follow(NDJSON 스트림)/tui(터미널 UI, 사진·답장 인용 지원)/serve(HTTP+SSE, openapi.json 계약)
  • Windows는 실행 중인 카카오톡 메모리에서 방별 키를 찾아 DB 읽기 + Win32 입력으로 전송. macOS는 기기 정보로 키 유도해 계정 DB 하나를 읽음(카톡 꺼져 있어도 읽기 가능) + Accessibility(AX)로 전송.
  • 2026-10-06 변경: saya 연결 방식이 "설정 적어넣기"에서 "자동 등록"으로 전환 (SAYAREGISTERURL/SAYAREGISTERTOKEN/SAYAADVERTISEURL 3개 env로 serve 자체등록).

saya (github.com/sanguneo/saya)

  • nichirin/tsuba의 HTTP+SSE 표면을 그리는 웹 클라이언트 (Bun 기반, bun run dev → localhost:5173). 자체 코어 로직 없음 — "날은 코어가 쥐고, 여기는 화면만".
  • "릿지(ledge)" UX 설계: 대화창을 가로지르는 1px 선 — 선 위는 "되읽어 확인된 전송", 선 아래는 "입력만 됨·전달 미확인". /send 응답에 메시지 id/nonce/전달확인이 없어서 생긴 설계 — 불확실한 전송을 자동 재전송하지 않음.
  • 계약(OpenAPI): /health, /rooms, /context, /digest, /stream(SSE: ready→message→cursor→ping), /send. 타입은 수기 작성 금지, bun run contract:generate가 계약 문서에서 자동 생성 + 해시로 바이트 동일성 검증.
  • 브라우저 제약 다수 명시: CORS 없음(동일 origin 필요), EventSource 불가(Bearer 헤더 때문에 fetch+ReadableStream 직접 구현), 동시 /stream 기계당 8개 제한, ID가 2^53 초과하는 문자열(Number() 변환 금지).
  • "화면이 약속하지 않는 것" 섹션: 방 미리보기 없으면 "미리보기 없음" 그대로 표시, 읽음 처리 라우트 없음(안읽음 배지=데스크톱 숫자 그대로), 과거 1000개 초과는 "닿지 않는 것"으로 표시 — 거짓 정보를 지어내지 않는 설계 원칙.

tsuba (github.com/sanguneo/tsuba)

  • 메신저 어댑터 모음 — 계약 버전 0.2.5, 공통 OpenAPI: /health, /capabilities, /icon, /rooms, /messages, /media, /stream, /send, /edit, /delete, /react, /read.
  • 구현된 어댑터 3종:
    • Telegram (mtcute 기반, 사용자 계정): 방 목록(쓰기 가능 여부 포함)/이전 메시지/첨부/커서 스트림(수정·삭제·반응)/전송·답장·수정·삭제·반응·읽음처리
    • Discord (discord.js, 봇 계정): 초대된 서버의 일반 텍스트 채널/이전 메시지/첨부/커서 스트림/전송·답장·수정·삭제·반응
    • Slack (공식 사용자 토큰 + Socket Mode, 내 계정): 채널/비공개채널/DM/그룹DM/이전 메시지/첨부/커서 스트림/전송·답장(스레드+채널)·수정·삭제·반응·읽음처리
  • GET /capabilities로 기능 신고 — "밝히지 않은 기능은 없는 것"이라는 명시적 원칙 (클라이언트는 신고된 것만 렌더링).
  • 새 메신저 추가 가이드(docs/custom-adapter.md) + 예제(examples/memo) 제공 — TypeScript 아니어도 계약에 답하고 saya에 등록하면 됨.

chatplus-core (github.com/sanguneo/chatplus-core)

  • SK텔레콤 채팅+ PC 클라이언트(Windows/macOS)의 로컬 캐시를 읽어 tsuba 어댑터 계약(0.2.7)으로 답하는 어댑터. TUI 없음, tsuba와 별도 저장소.
  • 읽기: rooms.list, messages.read(before 페이지네이션), messages.stream(SSE). 쓰기: messages.send(텍스트, maxLength 3072), attachments.send(이미지만, jpeg/png/gif, 최대 10MiB) — 클라이언트 창을 사람처럼 조작해서 전송.
  • 동작 원리(기술적으로 상세): Windows 자격증명 관리자의 16바이트 AES 키 → .secure cipher-key 파일(AES-GCM) 복호화 → 32바이트 Hive AES 키 획득 → Hive v2 박스 파일(folder.hive/object.hive, AES-256-CBC+PKCS7, CRC32 무결성) 복호화 → FastAPI가 tsuba 계약으로 응답. 읽기 전용, 발송 없음(API 레벨에서는).
  • macOS 버전은 동일 코드가 /Applications/ChattingPlus.app(com.sktelecom.torchlight)의 샌드박스 컨테이너 캐시를 읽음. Hive 키는 키체인이 아닌 shared_preferences(plist)에서 획득.
  • unread는 항상 0(캐시 읽음상태 미매핑), 토큰 32바이트 미만이면 서버 시작 안 함, 루프백 바인딩 전용.
