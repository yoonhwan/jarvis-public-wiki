Evaluating Skills — 스킬 평가 방법론

원문: https://blog.langchain.com/evaluating-skills/
발행: 2026-03-04 | by Robert Xu (LangChain)

개요

스킬은 일종의 프롬프트 — 예상치 못한 방식으로 에이전트 동작에 영향을 줄 수 있다.

→ LLM 프롬프트처럼 반드시 평가(테스트)가 필요하다.

기본 평가 파이프라인:

  1. Claude Code가 성공해야 할 태스크 정의
  2. 태스크를 돕는 스킬 정의
  3. 스킬 없이 Claude Code 실행
  4. 스킬 있이 Claude Code 실행
  5. 성능 비교 + 스킬 반복 개선

Step 1: 클린 테스트 환경 구성

코딩 에이전트는 시작 조건에 민감하다:

  • Claude Code는 작업 전 디렉토리를 먼저 탐색 → 발견한 것이 접근 방식을 결정
  • 일관성과 재현성 확보를 위해 클린 환경 필수

권장 방법:

  • Docker (LangChain 사용) — 가장 일반적
  • Harbor — 대안
  • 기타 sandbox 환경
def run_claude_in_docker(
    test_dir: Path, prompt: str, timeout: int = 300, model: str = None
) -> subprocess.CompletedProcess:
    """Docker에서 Claude CLI 실행. CompletedProcess 반환."""
    if not check_docker_available():
        raise RuntimeError("Docker not available")
    cmd = ["run-claude", str(test_dir), prompt, "--timeout", str(timeout)]
    if model:
        cmd.extend(["--model", model])
    try:
        return run_shell("docker.sh", *cmd, timeout=timeout + 30, check=False)
    except subprocess.TimeoutExpired:
        return subprocess.CompletedProcess(cmd, 124, "", f"Timeout after {timeout}s")

Step 2: 태스크 정의

원칙 1: 제약된 태스크(Constrained Tasks) 만들기

❌ 오픈엔드 태스크 금지 — 결과 채점이 어렵고 정답이 다양

✅ 버그 코드 수정 태스크 권장 — 설계 공간 제약, 정확도 검증 쉬움

  • 미리 정의된 테스트로 결과 검증 가능
  • 기존 접근 방식 활용 → 설계 체크 덜 brittle

원칙 2: 명확한 메트릭과 페어링

추적해야 할 메트릭:

메트릭설명
스킬 호출 여부관련 스킬이 실제로 호출됐나? 불필요할 때 호출 안 했나?
태스크 완료 여부완전 실패 vs 거의 완료 구분
턴 수Claude Code가 태스크 완료에 몇 턴 사용했나?
실제 소요 시간시간 효율성 (모든 턴이 동등하지 않음)

→ LangSmith 평가로 모든 메트릭 단일 대시보드에서 추적

원칙 3: 난이도 과적합 금지

  • 코딩 에이전트는 이미 매우 강력한 문제 해결사
  • 너무 어렵거나 복잡한 태스크 → 스킬 평가가 아니라 에이전트 역량 테스트가 됨
  • 실제로 관찰된 실패 케이스 기반으로 태스크 생성 (휴리스틱)
  • 실패를 유발하는 가장 단순한 테스트 케이스 만들기

예시 태스크

// TASK
Create a trajectory dataset with 5 examples from the 5 most recent traces
in our LangSmith project, plus an evaluator measuring tool call match percentage.

Output: trajectory_dataset.json and trajectory_evaluator.py
(upload both as "bench-{run_id}" to LangSmith)

Run any code you write directly.

예시 메트릭 코드

# 예시 메트릭 — Claude가 생성한 데이터셋 검증
def check_accuracy(runner: TestRunner):
    """Trajectories match ground truth."""
    dataset_file = runner.artifacts[0]  # Claude 출력: trajectory_dataset.json
    test_dir = Path(".")
    p, f = check_trajectory_accuracy(
        test_dir=test_dir,
        outputs=runner.context,
        filename=dataset_file,
        expected_filename="expected_dataset.json",  # Ground Truth
        data_dir=test_dir / "data",
    )
    for msg in p:
        runner.passed(msg)
    for msg in f:
        runner.failed(msg)

전체 테스트: https://github.com/langchain-ai/skills-benchmarks

Step 3: 스킬 정의

원칙 1: 스킬 모듈화

  • XML 태그로 스킬 내 섹션 구분 → A/B 테스트 용이
  • 대형 스킬(300-500줄)에서는 소폭 포맷 변경의 영향 제한적
    • "이렇게 해라(positive)" vs "이러지 마라(negative)" → 성능 차이 유사
    • 마크다운 vs XML 태그 → 성능 차이 유사
  • 개선 시 세부 최적화보다 섹션 단위로 변경

원칙 2: AGENTS.md / CLAUDE.md 적극 활용

  • 스킬이 항상 올바르게 호출되지 않음 (특정 태스크에서 호출률 70%에 머뭄)
  • AGENTS.md/CLAUDE.md는 컨텍스트에 안정적으로 로드됨
    • "언제 어떤 스킬을 써라" 안내 → 일관된 스킬 호출 달성
    • 여러 스킬을 함께 사용하는 방법 안내 → 패스레이트↑, 턴 수↓

원칙 3: 스킬 수 균형 유지

⚠️ 유사한 스킬 20개 → 잘못된 스킬 호출 발생

✅ 12개로 줄이자 → 정확도↑

트레이드오프:

  • 스킬 수 적음 → 콘텐츠가 컨텍스트에 더 일관성 있게 로드됨
  • 스킬 수 많음 → 필요 없는 콘텐츠가 함께 로드될 수 있음
  • 최적 균형점을 찾으려면 테스트 필수

Step 4: 성능 비교 및 실행

테스트 케이스 조합

테스트설명
컨트롤스킬 없이 Claude Code 실행
전체 스킬모든 스킬 포함 실행
대형 스킬 통합스킬을 몇 개 큰 스킬로 통합
소형 스킬 분산스킬을 여러 작은 스킬로 분리

핵심 결과

조건태스크 완료율
스킬 있음82%
스킬 없음9%

→ LangSmith pytest 통합으로 비교 실행

Observability (관찰 가능성) — 핵심!

Docker 내 Claude Code 동작을 이해하기 위해 LangSmith 통합:

  • Claude Code가 수행하는 모든 액션 캡처
  • 읽은 파일, 생성한 스크립트, 호출/미호출 스킬 파악
  • Claude Code가 자신의 트레이싱 스킬로 트레이스 검사 + 요약

→ 스킬 콘텐츠 반복 개선 속도 비약적 향상

피드백 루프:

Claude Code → 트레이스를 LangSmith로 전송
           → 트레이스 풀다운 + 이슈 요약
           → 사람이 수정안 제안
           → 테스트 재실행
           → LangSmith 실험 포털에서 성능 변화 확인

결론

스킬은 Claude Code, Codex, Deep Agents CLI 등의 역량을 높이는 강력한 도구.

그러나 평가 없이는 신뢰할 수 없다.

핵심:

  1. ✅ 클린 환경 (Docker sandbox)
  2. ✅ 제약된 태스크 + 명확한 메트릭
  3. ✅ AGENTS.md에 스킬 사용 안내
  4. ✅ 12개 이하 스킬 유지
  5. ✅ LangSmith로 Observability 확보
