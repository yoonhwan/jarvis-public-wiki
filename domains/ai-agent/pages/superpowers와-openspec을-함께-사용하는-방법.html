Superpowers와 OpenSpec을 함께 사용하는 방법

원본: https://www.threads.com/@writedev.san/post/DWJymCTkv-t

요약

superpowers와 openspec 두 도구를 구현 규모에 따라 다르게 조합하여 사용하는 워크플로우를 제안하는 글. 핵심은 "변경 크기에 따라 워크플로우를 나누는 것"이며, 사양(spec)을 항상 최신 상태로 유지하는 것이 프로젝트 중후반부 비용을 줄이는 핵심이라고 강조한다.

두 도구의 강점

도구강점
superpowers심층적인 브레인스토밍, TDD, 동시 구현 (멀티 에이전트 오케스트레이션)
openspec사양을 항상 최신 상태로 유지. main spec + delta spec 구조
  • delta spec: 이번 변경에 대한 사양. 구현 완료 후 main spec에 반영됨.
  • 항상 최신 사양 안에서 논의와 구현이 진행됨.

구현 규모별 워크플로우

1. 규모가 큰 구현/수정

초기 구현이나 큰 기능, 기존 구현의 대규모 변경.

1.1 superpowers로 구현

/superpowers:brainstorming    → 구현 방향 논의
/superpowers:write-plan       → 구체적 구현 계획 작성
/superpowers:execute-plan     → 구현 실행

1.2 openspec으로 사양 동기화

/opsx:propose    → superpowers plan 기반으로 사양 생성 (이미 구현 완료이므로 tasks 전부 완료 처리)
/opsx:archive    → delta spec을 보관하면서 main spec과 동기화

2. 규모가 크진 않지만 사양이 필요한 구현

기존 openspec 워크플로우를 그대로 사용:

/opsx:propose → /opsx:apply → /opsx:archive

superpowers의 심층 계획이 불필요하지만, 사양은 남겨야 하는 규모.

3. 규모가 작은 구현/수정

별도 사양 작성이 번거로운 작은 수정들:

  • 에이전트로 바로 수정
  • spec-patch 커맨드로 사양에 반영
작은 수정이라도 사양에 반영하지 않으면, 에이전트가 원하는 방향과 다른 제안을 하고, 정책과 다른 수정을 하기 쉬움. 누적되면 이전 자료를 다시 찾아 인지시키거나, 자료가 없으면 재조사/재분석 필요 → 시간·토큰 낭비.

Inline Spec Patch: OpenSpec Inline Spec Patch — ad-hoc 수정을 main spec에 직접 반영하는 커맨드

핵심 정리

변경 규모워크플로우
큰 수정superpowers로 계획·실행 → openspec으로 spec 동기화
중간 수정openspec 워크플로우로 처리
작은 수정바로 수정 → spec-patch로 동기화

저자의 인사이트

  • 사양 유지에 토큰 소모는 있지만, 프로젝트 중후반부로 갈수록 사양 없이 진행하는 쪽이 더 큰 소모를 만든다.
  • 에이전트가 이전 결정을 모르면 시행착오가 반복되고, 매번 다시 맥락 설명 → 시간·토큰·피로도 누적.
  • "이 방식이 저한테는 꽤 잘 맞고 있습니다."
