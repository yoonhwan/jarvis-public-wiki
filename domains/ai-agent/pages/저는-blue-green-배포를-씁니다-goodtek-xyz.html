저는 Blue/Green 배포를 씁니다 (goodtek.xyz)

본문 (Main Post)

  • 배포 때문에 서비스가 멈추는 게 정말 싫다. 특히 고객이 쓰는 서비스라면 몇 초의 다운타임도 치명적일 수 있다.
  • Blue/Green은 기존 서비스는 그대로 두고, 새 버전을 먼저 띄워 테스트한다.
    • 정상이면 트래픽만 새 버전으로 전환
    • 문제가 생기면 바로 기존 버전으로 되돌리면 끝
  • 서비스를 끄고 배포하는 게 아니라, 새 버전을 준비한 뒤 교체하는 방식.
  • 조금 번거롭더라도 운영해 보면 왜 다들 Blue/Green 배포를 쓰는지 알게 된다.

댓글 스레드 (Reply Thread / Other Users)

Blue/Green + Canary 조합

  • 이전 회사는 blue/green + canary 배포를 사용.
    • blue = 기존 live 인스턴스들, canary green 하나가 투입되어 일정 시간 테스트 트래픽을 받다가 이상이 없으면 blue와 동일해질 때까지 점진적으로 트래픽을 높여 전환.
  • 단순 Blue/Green은 스위치 순간 모든 사용자가 새 버전을 사용 → 치명적 버그 시 전 사용자가 동시에 영향.
  • Canary는 실제 사용자 일부에게만 노출하여 문제를 조기 발견 가능.

규모에 따른 선택

  • 카나리도 블루그린도 적절히 필요할 때가 있음.
  • 블루그린은 두 배의 자원이 떠 있어야 하는 점 때문에 일정 규모 이상에서는 부담.
  • 의외로 버그패치나 기능 배포는 카나리로 충분한 경우도 많음.
  • → 항상 적용보다는 사이즈/규모 보고 적절한 스택 선정이 맞다.

DB / 롤백 관련

  • DB는 배포 대상이 아니다.
  • DB 구조가 바뀌면 롤백 시 오류가 생길 수 있음.
  • 보통 DB는 수작업 배포를 하지만, 요즘은 마이그레이션 파일을 두고 db:migrate로 배포에 함께 묶기도 함.
    • 이 경우 롤백도 쉬움. ORM 붙이면 더 쉬워짐.
