AG-UI — 에이전트와 사용자 앱을 잇는 오픈 프로토콜

에이전트를 서비스 화면에 붙일 때 필요한 „에이전트 ↔ 사용자 앱" 통신을 표준화한 오픈 프로토콜. 에이전트가 타입이 붙은 이벤트 스트림을 내보내면, 어떤 프레임워크로 만들었든 아무 클라이언트(웹·모바일·터미널·Slack)나 그 이벤트를 렌더한다. 스펙 1.0이 동결됐고 TypeScript·Python·.NET SDK가 스펙에서 생성된다.

  • 어떤 에이전트든 웹·모바일·Slack·터미널에 연결.
  • 스트리밍 채팅, 생성형 UI, 공유 상태 지원.
  • 프론트엔드 도구 호출.
  • 사람 승인·수정·거절 후 이어서 실행.
  • 추론 표시, 서브에이전트, 멀티모달까지 지원.
  • 핵심 구도: AG-UI = 에이전트 ↔ 사용자, MCP = 에이전트 ↔ 도구·데이터, A2A = 에이전트 ↔ 다른 에이전트.
  • LangChain, CrewAI, Google ADK, Microsoft Agent Framework 등과 연결. TypeScript·Python·.NET SDK 제공. MIT 오픈소스, 현재 약 1.9만 스타.

원문 링크: https://github.com/ag-ui-protocol/ag-ui

3층 구도 — AG-UI · MCP · A2A

공식 문서는 AG-UI를 „에이전트 프로토콜 생태계의 세 번째 축"으로 규정한다. 셋은 경쟁이 아니라 층이 다르고, 한 에이전트가 셋을 동시에 쓴다.

프로토콜잇는 것역할판단
AG-UI에이전트 ↔ 사용자사용자 앱과 에이전트 사이 이벤트 스트림화면·상호작용 층. MCP·A2A 에이전트를 „앞단에서 대신 받는(front for)" 핸드셰이크 지원
MCP에이전트 ↔ 도구·컨텍스트도구·데이터 연결도구 층. 도구 자체가 에이전트화되는 추세
A2A에이전트 ↔ 에이전트에이전트 간 협업협업 층

생성형 UI 스펙(A2UI, MCP Apps, Open-JSON-UI)과는 역할이 다르다. 그 셋은 „에이전트가 어떤 UI를 보여주고 싶은지"를 서술하고, AG-UI는 그 페이로드를 포함한 모든 이벤트를 나르는 런타임 프로토콜이다.

동작 방식

  1. 앱이 RunAgentInput 하나를 보낸다 — 대화, 프론트엔드가 제공하는 도구, 공유 상태, 컨텍스트.
  2. 에이전트는 8계열 · 31종의 타입 이벤트를 스트림으로 돌려준다.
  3. 필수는 run 라이프사이클뿐이다. 최소 에이전트는 몇 개 이벤트만 내보내고 거기서 확장한다.

전송 계층은 고정하지 않는다. 스펙은 HTTP+SSE와 HTTP+Protobuf(바이너리) 바인딩을 정의하고, WebSocket 등 다른 전송은 미들웨어로 붙인다. 이벤트 구조도 AG-UI 형식과 정확히 일치할 필요는 없고 „호환되면" 된다 — 기존 프레임워크가 자기 이벤트를 최소 수정으로 변환한다.

1.0 스펙과 시작점

  • 1.0 동결: JSON Schema 기반의 안정 스펙. TS·Python·.NET SDK가 스펙에서 생성된다.
  • 양방향 호환: 0.x 에이전트와 1.0 클라이언트, 그 반대 조합 모두 동작.
  • 최소 구현은 „HTTP 엔드포인트 하나 + RunAgentInput 받고 이벤트 스트림 반환"이다. README 예제는 Python 3.9+ 에서 ag-ui-protocol·FastAPI·uvicorn 만으로 30줄 서버·클라이언트를 보여준다.
  • 앱 스캐폴딩은 npx create-ag-ui-app@latest — CopilotKit(Next.js) 또는 터미널 클라이언트를 고른 프레임워크에 연결한다. 생성 템플릿은 OpenAI를 호출하므로 OPENAIAPIKEY가 필요하다(README 예제 서버는 키 불필요).

사람 개입(HITL) 설계 포인트

문서 기준으로 „사람이 승인·수정·거절 후 이어서 실행"은 run이 interrupt 결과로 끝나고, 사용자 결정 후 다음 run이 이어받는 구조다.

  • 실행을 멈춘 채로 세션을 붙잡고 있지 않는다 → 승인 대기 시간이 인프라 비용이 되지 않는다.
  • 승인 대기 중 상태는 STATESNAPSHOT/STATEDELTA로 앱과 동기화되고, 재개 시 같은 thread에서 run을 새로 시작한다.
  • 이 구조는 „오래 떠 있는 에이전트의 유휴 비용" 문제와 직결된다. 같은 주제를 다룬 타 계정 게시글도 유휴 시간이 실제 작업의 20% 수준이라며 비용 최적화를 논한다(수치는 그 계정 주장, 원 출처 미확인).
