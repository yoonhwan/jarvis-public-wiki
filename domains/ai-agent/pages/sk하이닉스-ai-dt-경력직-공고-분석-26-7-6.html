핵심 한 줄

이 공고는 AI 개발자를 뽑는 것처럼 보이지만, 실제로는 반도체 P&T(Package & Test) 현장을 이해하고 AI로 서비스화할 수 있는 "AI 서비스 엔지니어" 를 찾는 공고에 가깝다.

  • P&T = 웨이퍼에서 만든 칩을 패키징·검사·모듈화하고 최종 품질을 검증하는 영역
  • 연구용 AI가 아니라 현업이 매일 쓰는 AI 서비스를 만들 사람을 원함

1. 자동화 vs 지능화

  • 자동화: 단순 반복 업무 축소 (데이터 조회, 리포트 작성, 이상 이력 검색, 조건 비교, 문서 요약, 알람 분류)
  • 지능화: 한 단계 더 깊음 — 상황을 이해하고 → 관련 데이터를 찾고 → 가능한 원인을 좁히고 → 다음 액션을 제안
  • 따라서 AI Agent는 챗봇 수준에서 끝나면 안 됨. "지금 어떤 문제인지 / 어떤 데이터를 봐야 하는지 / 과거 유사 사례는 / 담당자는 어떤 판단을 내려야 하는지"까지 지원해야 함.

2. 공정별 의사결정 방식 (HBM, PKG, TEST, WT, Module)

공정봐야 할 것
HBM적층 구조, 수율, 열, 신뢰성, 패키지 특성
PKG공정 조건, 장비 상태, 소재, 접합 품질, Warpage / Crack / Void
TEST전기적 특성, Bin 분류, Fail Pattern, 장비 조건, 제품 스펙, 고객 품질 요구
WT웨이퍼 단위 전기 검사 결과 → 불량 패턴·공정 원인 추정
Module조립 품질, 동작 안정성, 테스트 결과, 고객 요구 수준
"복잡한 의사결정" = 데이터가 많다는 뜻이 아니라, 공정·장비·품질·제품·일정·수율·고객 요구가 동시에 얽혀 있다는 뜻.

3. Agentic AI의 실제 역할 (불량 발생 시)

공정 조건 / 장비 Drift / 소재 Lot / 검사 기준 / 제품 설계 / 이전 공정 영향인지 빠르게 좁혀야 함. 이때 Agent가:

  • MES에서 Lot 이력 가져오기
  • FDC에서 장비 센서 데이터 확인
  • 과거 불량 사례를 RAG로 검색
  • 관련 문서·Spec 요약
  • 가능성 높은 원인 후보 정리
  • 담당자에게 다음 확인 항목 제안
AI Agent는 사람을 대체하는 도구가 아니라 경력자의 판단 속도를 높여주는 의사결정 보조 시스템.

4. 필요한 사람 = 단순 Python 개발자(X)

  • LLM을 서비스로 구현할 수 있어야 함
  • RAG를 도메인 지식 기반으로 설계
  • Vector DB + Prompt Engineering 이해
  • LangChain, LangGraph 활용
  • 그리고 현장 Legacy / MES / FDC / 장비 데이터와 연결까지
  • "AI PoC 경험"보다 실제 프로덕션 배포 + 현업 반복 사용 + 운영 중 오류·개선 대응 경험이 더 강함

5. 선도 기술 = 멋으로 쓰는 게 아님

P&T 현장의 생산 효율·수율·품질 경쟁력과 연결하겠다는 의미:

  • RAG: 현장 문서, 공정 기준서, 장비 매뉴얼, 불량 사례, 조치 이력 검색
  • AI Agent: 여러 시스템을 오가며 조회·분석·액션 추천
  • Digital Twin: 공정·장비·물류·품질 상태를 가상 환경에서 시뮬레이션·예측
  • 발전 방향: Agent ↔ Digital Twin 연결 → "이 조건을 바꾸면 수율/병목이 어떻게 변할지" 사전 검토

6. 자소서·면접 표현 (경력직)

"LLM 써봤습니다"는 약함. 이렇게 말해야 함:

어떤 현업 문제를 정의했고 → 어떤 데이터를 연결했고 → 어떤 Agent 구조를 설계했고 → 어떤 시스템과 연동했고 → 실제 사용자가 어떤 업무에서 활용했으며 → 운영 후 어떤 개선 효과가 있었는가

요구 자격: CS/SW/AI/전산 지식 기본, Python 데이터 분석 + LLM 앱 개발 경력 2년 이상, LangChain/LangGraph(=실무형 LLM 경험), Transformer/Prompt Engineering/RAG/Vector DB 이해(=단순 API 호출자 X).

7. 커뮤니케이션 역량

"비전공자인 현업 담당자와도 원활히 소통" — 절대 가벼운 조건 아님. 공정·장비·품질·제조 담당자와 계속 대화해야 함. 현업은 "RAG 성능"보다 "그래서 내 문제가 해결되느냐" 를 봄.

좋은 지원자 = 기술 용어를 현업 언어로 번역하고, 현업의 모호한 요구를 기술 요구사항으로 정리.

8. 우대 경험

  1. 실제 현업 문제 분석 → Agent 구현·운영 (PoC가 아니라 문제 정의 → 설계 → 배포 → 피드백 → 운영 개선)
  2. Multi-Agent 시스템 (데이터 조회 / 문서 검색 / 이상 탐지 / 원인 분석 / 리포트 생성 Agent 협업)
  3. 서비스 배포 경험 (모델 제작보다 운영 환경에서 안정적으로 돌리는 능력)

9. 결론 — 이 공고에 맞는 사람

AI 모델 이해 + LLM 앱 제작 + RAG/Vector DB 이해 + LangChain/LangGraph Agent 구현 + 현장 데이터 연결 + MES/FDC/장비 시스템 이해 + 비전공자 소통 + 무엇보다 만든 AI를 실제 현업 서비스로 운영해 본 사람.

피해야 할 답변 → 바꿔야 할 답변

피해야 할 답변바꿔야 할 표현
"LLM으로 챗봇 만들었습니다"어떤 현업 문제였는지
"Python으로 데이터 분석했습니다"왜 Agent가 필요했는지
"RAG 구현했습니다"어떤 데이터를 연결했는지 / RAG 지식베이스 구성법
"현업과 협업했습니다"Agent가 어떤 판단 흐름을 지원했나 / 배포 후 업무가 어떻게 바뀌었나

10. 공고를 잘 읽는다는 것

경력직 공고는 스펙 나열이 아니라 회사가 지금 겪는 문제의 힌트. 이번 공고의 힌트:

  • "P&T 현장은 복잡하다"
  • "현업 의사결정은 느리고 어렵다"
  • "LLM Agent로 그 판단을 빠르고 정확히 돕고 싶다"
  • "단, 실제 현장에서 돌아가는 서비스여야 한다"

경험 정리 흐름:

문제 정의 → 데이터 연결 → Agent/RAG 설계 → 시스템 연동
→ 서비스 배포 → 현업 활용 → 운영 개선 → 성과
공고를 잘 읽는다는 건 = 내 기술을 회사의 문제 언어로 번역하는 일.

  • 회사 에피소드 몇 개가 합격을 이끄는 게 아니라, 의뢰인의 이야기 안에서 지원처에 맞물리는 소스를 뽑아 연결하는 능력이 중요
