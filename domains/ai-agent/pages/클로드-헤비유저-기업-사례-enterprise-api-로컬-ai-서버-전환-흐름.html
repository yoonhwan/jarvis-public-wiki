본문 (Main Post — 작성자 연속 게시, 7편)

1. 도입 — 클로드 헤비유저를 만난 충격

클로드 헤비유저(들)을 만나고 진짜 충격먹었습니다…

클코 맥스 구독권을 몇개 쓰는지 물어봤더니,

  • 구독해서 쓰면 제약이 너무 많다
  • 가장 큰 이유로는 hourly / weekly limit이 너무 적고
  • 리밋에 걸리면 모든 작업이 멈추며
  • 계정마다 세션이 공유가 안 되고
  • 계정마다 메모리 + 스킬 셋업도 매우 귀찮고
  • 애초에 다중 구독은 ToS 위반이기도 하며
  • Scalable한 셋팅이 어렵다.

그러면 어떻게 해요…? 라고 물어봤을 때 답변이 정말 흥미로웠는데 (이어서)

2. 답변 — Enterprise API

바로 Enterprise API를 이용한다는 것.

  • hourly/weekly limit이 없고
  • 리밋이 없으니 작업이 멈출리가 없고 (24시간 구동)
  • 계정 단위로 세션 공유가 가능하고
  • 팀원끼리 memory + skill이 공유가 가능하고
  • 무엇보다 scalable하게 사용이 가능하다.

Scalable하게 쓸 수 있다는건, 필요에 따라 CPU+메모리만 확장하면 무한정으로 작업 처리량을 늘릴 수 있다는 것. AWS와 연결해서 유동적으로 워크로드를 해결할 수도 있고, 내부 compute farm에도 연결할 수 있다.

직원을 늘리는게 아니라, 인당 쓸 수 있는 agent의 수를 늘려주는 것. 같이 대화를 나눴던 분은 서버 인스턴스만 혼자 20개 쓴다고 하셨다. (작성자는 6개)

일단 여기서 1차 충격.

3. 24시간 구동 이유

'24시간이나 돌일 일이 있나요?' 라는 질문에 살짝 어이없다는 표정을 지으면서 말하길

  • CI/CD도 24시간 돌리는데, 기능 개발과 버그 수정도 24시간 돌아야하지 않겠냐
  • 사람은 8시간 일하고, 가족이랑 시간 보내고, 밥먹고, 자고 해야하지만
  • 컴퓨터는 잠도 안자고 전기만 먹이면 되니까, 그걸 이용해야한다

듣고보니 맞는 말이라 2차 충격

4. Safety-critical 코드 검토 체계

'근데 AI가 실수하면 어떡해요? 그쪽 코드는 버그나면 사람이 죽을수도 있는 safety critical 코드잖아요.'

  • Hardware-in-loop 시뮬레이션까지도 다 연결해놨다.
  • 사람의 검토가 필요한건 계속 쌓아두는 편인데
  • 하루에 사람이 8시간 검토만 해도 이게 처리가 다 안되기도 하더라
  • 그래서 글로벌 팀을 꾸려서, 각각 다른 타임존의 사람끼리 8시간씩 3교대 돌아가며 24시간 보고있다

개발은 AI가, 검토는 사람이. 그리고 체계적인 개발-검토 사이클을 돌리기 위한 시스템 재개편에 3차 충격.

5. 비용

'비용 많이 나오지 않나요?'

  • 많이 나온다. 개발자가 300명정도 되는데, 인당 평균 매달 5천 USD 정도 쓰고, 헤비 유저는 2만 USD 정도 쓴다.
  • 비싼거 안다. 근데 그정돈 써야한다. 지금의 개발 속도를 포기할 순 없기에
  • 이걸 내려놓으면 경쟁에서 지는거고, 경쟁에서 이기면 이거보다 더 많이 버니까 괜찮다.
  • 옆 회사는 클로드 구독권도 안준다는데, 우리가 이렇게 투자해서 앞서나간만큼 간격을 벌리는거다. 이 간격은 다시는 좁혀지지 않는다.

'헉 근데 매달 100만 달러는 너무한거 같은데요'

  • 우리도 안다. 예상했던 비용보다 더 많이 나왔다.
  • 그래서 자연스럽게 1. 토큰량을 줄이는 하네스 제작, 2. 로컬 AI 서버 설치를 고민하게 되더라.

그리고 대부분의 회사는 '로컬 AI 서버 설치' 로 기울게 되는 것 같다.

6. 로컬 AI 서버 설치 시 장점

로컬 AI 서버를 설치하게 될 경우

  1. 무한 토큰 생성 가능
  2. 비공개 코드가 anthropic에 넘어가서 학습에 이용되지 않음
  3. 오픈 웨이트 모델 나올 때 마다 업데이트 가능
  4. AI 서버가 비싸긴 하다만, 회사의 자산으로 처리 가능
  5. 추후에 더 좋은 모델이 나오면, AI 서버는 LLM이 아닌 다른 용도로 사용 가능

어차피 토큰 줄이는 하네스는 Anthropic이나 다른 컨트리뷰터가 만들 것 같다~ 직접 만들 필요가 없음, 이라고 얘기하는데 @bellman.pub 이 생각나게 되고… 초거대 LLM (Kimi 1T 급 모델)을, 버그없이 안정적으로, 많은 사람들에게, 오래 서빙할 수 있는 서버를 찾기만 한다면 투자를 할 가치가 있다고 판단한다고 한다.

7. 가장 큰 병목 2가지

그리고 현재 이렇게 AI 쓰면서 돌릴 때 생기는 가장 큰 병목은 2가지였는데

  1. Anthropic의 서비스 불안정성
  2. Agentic 하게 돌면서 CPU 연산이 너무 느림

진짜 깜짝 놀랐는데, 거의 80-90%는 토큰 생성이 아니라 execution이라고 한다. LLM은 빠릿빠릿하게 잘 도는데, 파이썬 코드가 돌거나 라이브러리 빌드하는 시간이 너무 길다는 것. 그동안 LLM이 아무것도 안하고 로그 읽으면서 토큰 낭비하는게 너무 열받는다고.

그래서 고성능에 코어수 많고 캐시량 빵빵한 CPU가 필요하다는데, 이게 수급이 상당히 어렵다고.

"B200을 8장 꽂은 서버도, CPU는 고작 1개잖아. 물론 아무도 H200에서 agentic ai 안하겠다만" 라는 말이 얼마나 충격이였는지.
