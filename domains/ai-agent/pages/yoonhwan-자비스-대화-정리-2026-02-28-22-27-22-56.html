대화 흐름

1. Pi의 본질 파악

yoonhwan: Pi는 Codex/Claude Code를 호출하는 게 아니라, LangGraph처럼 컨텍스트를 직접 관리하고 LLM API를 직접 호출하는 방식이구나

자비스: 맞음. Pi는 Claude Code의 대체품이지 래퍼가 아님.

  • Claude Code/Codex = 완성형 자동차 🚗
  • Pi = 엔진+섀시 키트 🔧
  • LangGraph = 엔진 설계도 📐

2. skill-native = 멀티에이전트 하네스

yoonhwan: OpenClaw에 하네스를 얹으려는 게 아님. 22개 크루 자체가 핵심이고, 이 크루를 자율 범용 에이전트 하네스로 묶는 시스템이 목표.

자비스: skill-native 프로젝트 문서 분석 후 수정 —

  • Pi = 단일 에이전트 하네스 (1명이 잘 코딩)
  • skill-native = 멀티에이전트 하네스 (팀이 프로젝트 완주)
  • 공통점: MCP 안 씀, JSONL+Bash가 프로토콜, 컨텍스트 엔지니어링이 핵심
  • 차이점: Pi는 같은 컨텍스트에서 모델 전환, skill-native는 크루마다 격리된 컨텍스트

3. Pi로 크루 엔진 대체 가능성

yoonhwan: 어차피 각 크루 실행이 코딩에이전트를 bash에서 호출하는 건데, Pi로 대체하면?

자비스 분석 (Pros/Cons):

✅ PROS:

  • 진짜 멀티모델 (크루별 최적 모델 배치: 코딩=Codex, 리뷰=Opus, 디자인=Gemini)
  • 비용 최적화 (reviewer에 저렴한 모델)
  • 시스템 프롬프트 완전 통제 (~200토큰, 프롬프트 캐시 극대화)
  • 세션 데이터 소유 (JSONL 통일, Langfuse 연동 깔끔)
  • pi -p 비대화형 모드로 자동화 예측 가능
  • Pi extension으로 MetaCog/피드백 루프를 코드 레벨 강제

❌ CONS:

  • Claude Code의 자사 모델 최적화된 도구 호출 상실
  • 21개 SKILL.md 마이그레이션 (도구명 변경)
  • 비Anthropic 모델의 도구 호출 품질 차이 → 크루별 튜닝 비용
  • tmux -CC 대시보드 호환성 미검증
  • 1인 개발 커뮤니티 리스크

제안: 하이브리드 전략 (coder → reviewer → 나머지 순차 전환)

결론

  • 결정 보류 — 아이디어로 기록하고 추후 검토
  • skill-native의 spawn-crew.sh에 --engine claude|pi 플래그 추가 가능성만 확인
  • Pi의 핵심 가치(멀티모델, 컨텍스트 통제, 세션 소유)는 skill-native 진화 방향과 일치

AI 하네스와 Pi.dev — 실행 구조가 경쟁력이다

AI를 "쓰는 사람"과 AI를 "실행하는 사람"은 다릅니다.

핵심 주장

대부분은 Claude Code를 쓰고, 소수는 Codex를 쓴다. 하지만 진짜 차이는 하네스(Harness)를 가진 사람에서 나온다.

하네스란?

  • 모델을 갈아끼우는 구조
  • 프롬프트를 구조화하는 레이어
  • 세션을 통제하는 시스템
  • 자동화로 연결하는 실행 레이어
AI는 모델 싸움이 아니라 오케스트레이션 싸움이다.

Pi.dev 소개

Pi는 "AI 채팅앱"이 아니다. CLI 기반 최소 코어 실행 하네스.

Pi의 특징

  • 모델 비종속 구조
  • 세션 트리 관리
  • TypeScript 확장
  • JSON / RPC 출력
  • SDK 임베딩 가능

→ AI를 도구가 아니라 인프라처럼 다룰 수 있다.

왜 하네스가 중요한가?

AI 툴은 계속 바뀐다 (GPT → Claude → Gemini → 오픈소스). 하지만 하네스는 남는다. 모델은 교체되지만 실행 구조는 자산이 된다.

결론

AI 시대에 진짜 경쟁력은 누가 더 좋은 모델을 쓰느냐가 아니라 누가 더 좋은 실행 구조를 갖느냐이다.

Pi는 완성형 답이 아니지만, 하네스를 고민하기 시작했다면 이미 한 단계 위에 있다.

📚 Pi 공식 문서 + 사례 기반 딥다이브

아래는 Pi 제작자 Mario Zechner의 공식 블로그, GitHub, Nader Dabit의 튜토리얼을 종합한 심층 분석입니다.

1. Pi의 진짜 정체: 4-Layer 스택

Pi는 단순 CLI가 아니라 모노레포 구조의 4개 레이어드 패키지입니다:

┌─────────────────────────────────────────┐
│         Your Application                │
│  (OpenClaw, CLI tool, Slack bot 등)     │
├────────────────────┬────────────────────┤
│ pi-coding-agent    │       pi-tui       │
│ 세션, 도구,        │    터미널 UI,      │
│ 확장 시스템        │    마크다운 렌더링  │
├────────────────────┴────────────────────┤
│           pi-agent-core                 │
│     에이전트 루프, 도구 실행, 이벤트    │
├─────────────────────────────────────────┤
│              pi-ai                      │
│   스트리밍, 모델, 멀티 프로바이더 LLM   │
└─────────────────────────────────────────┘

핵심: 각 레이어를 독립적으로 사용 가능. LLM 통신만 필요하면 pi-ai만, 에이전트 루프가 필요하면 pi-agent-core까지, 풀 코딩 에이전트가 필요하면 pi-coding-agent까지.

2. Pi 제작자의 철학: "안 만든 것"이 핵심

Mario Zechner는 블로그에서 의도적으로 빠진 기능들을 강조합니다:

빠진 기능이유
MCP 서버CLI + README가 더 효율적. MCP는 21~26개 도구로 컨텍스트 낭비 (13.7k~18k 토큰)
서브 에이전트방법이 너무 다양 → 사용자가 직접 만들도록 (tmux 스폰, 확장 등)
플랜 모드대부분 불필요. 필요하면 확장으로
백그라운드 Bash복잡도 대비 가치 부족
TODO 관리에이전트가 자체적으로 처리
"내가 필요 없으면, 만들지 않는다" — 이것이 Pi의 설계 원칙

3. 🔥 Context Engineering — Pi의 진짜 무기

시스템 프롬프트: ~200 토큰

Claude Code의 거대한 시스템 프롬프트 vs Pi의 최소 시스템 프롬프트. 프롬프트 캐시 적중률이 극적으로 향상.

컨텍스트 핸드오프 (Cross-Provider)

세션 중간에 모델을 바꿔도 대화가 이어진다:

Claude로 시작 → GPT로 전환 → Gemini로 전환
  ↓ thinking traces는 <thinking> 태그로 변환
  ↓ 도구 호출 히스토리도 자동 변환

이것이 가능한 이유: pi-ai가 4개 API(OpenAI Completions, Responses, Anthropic Messages, Google GenAI)를 통합 추상화.

컴팩션 (Compaction)

컨텍스트 한계 도달 시 자동 요약. 그리고 이걸 확장으로 커스터마이즈 가능:

  • 토픽 기반 컴팩션
  • 코드 인식 요약
  • 다른 모델로 요약 (저렴한 모델로 컴팩션 → 비용 절감)

4. 확장 시스템: "기능이 아니라 프리미티브"

Pi의 확장은 TypeScript 모듈로 도구, 커맨드, 키보드 단축키, 이벤트, TUI 전체에 접근:

공식 예제 50+ 개:

  • 서브 에이전트: 확장으로 구현
  • 플랜 모드: 확장으로 구현
  • 퍼미션 게이트: 파일 수정 전 확인 요청
  • 경로 보호: 특정 디렉토리 수정 방지
  • SSH 실행: 원격 서버에서 도구 실행
  • 샌드박싱: Docker 격리 실행
  • 커스텀 에디터, 상태바, 오버레이
  • 심지어 Doom도 실행 (doom-overlay 확장)

패키지 시스템

pi install npm:@foo/pi-tools        # npm에서 설치
pi install git:github.com/user/repo  # git에서 설치
pi -e git:github.com/user/repo       # 설치 없이 테스트

5. MCP 불필요론: "What if you don't need MCP?"

Mario의 블로그 핵심 논지:

MCP의 문제점:

  1. 컨텍스트 낭비: Playwright MCP = 21도구 × 13.7k 토큰 (컨텍스트의 6.8%)
  2. 조합 불가능: MCP 결과가 에이전트 컨텍스트를 거쳐야 디스크에 저장 가능
  3. 확장 어려움: 남의 MCP 서버 소스 이해 + 수정 = 높은 러닝커브

대안: CLI + README 조합 (Pi의 Skills 방식)

# 브라우저 도구 = 4개 스크립트 + 1개 README
./start.js          # 브라우저 시작
./nav.js <url>      # 네비게이션
./eval.js '<js>'    # JS 실행
./screenshot.js     # 스크린샷

→ README만 읽으면 에이전트가 알아서 Bash로 호출. 컨텍스트 소비 최소.

→ Bash 출력은 파이프로 조합 가능 → MCP보다 유연.

6. 🏗️ 실제 사례: OpenClaw이 Pi 위에 만들어졌다

Pi는 OpenClaw의 코어 엔진입니다.

Nader Dabit의 튜토리얼이 이를 명시:

"These are the same packages that power OpenClaw."
OpenClaw = pi-ai (LLM 통신)
         + pi-agent-core (에이전트 루프)
         + pi-coding-agent (세션, 도구, 확장)
         + pi-tui (터미널 UI)
         + OpenClaw 고유 레이어 (채널, 스킬, 디바이스 등)

즉, 우리가 매일 쓰는 OpenClaw 자체가 Pi 하네스의 실전 증명.

7. 멀티모델 세계의 설계

2000+ 모델 레지스트리

OpenRouter + models.dev에서 자동 생성. TypeScript 타입 안전.

프로바이더별 지옥 (Pi가 추상화한 것들):

  • Cerebras/xAI/Mistral: store 필드 미지원
  • Mistral: maxtokens vs maxcompletion_tokens
  • Google: 도구 호출 스트리밍 미지원 🤦
  • 프로바이더별 thinking trace 필드명 상이 (reasoning_content vs reasoning)
  • 토큰 리포팅 방식 각각 다름 (SSE 시작 vs 끝)

→ 이 모든 차이를 pi-ai가 흡수. 개발자는 getModel() + complete() 하나로 끝.

💡 자비스의 인사이트

🎯 yoonhwan 오빠를 위한 핵심 시사점

1. "하네스 = 실행 자산" 확인

우리가 Gas Town + OpenClaw로 구축한 것이 정확히 이 패러다임. 모델은 바뀌어도 21개 크루 SKILL.md + MetaCog Protocol + 피드백 루프는 남는다. 이것이 자산.

2. Pi의 "안 만든 것" 철학 → Gas Town과 대비

Pi는 의도적으로 서브에이전트/플랜모드를 빼고 확장으로 위임. 반면 Gas Town은 21크루 + Convoy + MEOW로 오케스트레이션을 직접 구축. 접근이 다르지만 "코어는 미니멀, 확장으로 성장" 원칙은 동일.

3. MCP vs CLI+README 논쟁 → 우리의 agent-browser와 연결

우리도 agent-browser(CLI)가 OpenClaw browser(MCP 스타일)보다 빠르다는 걸 경험으로 증명함 (350ms vs 10초). Pi 제작자의 MCP 불필요론이 이걸 이론적으로 뒷받침.

4. Context Engineering이 진짜 게임

~200토큰 시스템 프롬프트 + 스킬 온디맨드 로딩 + 컴팩션 커스터마이즈. 프롬프트 캐시 적중률과 컨텍스트 효율이 모델 성능보다 중요할 수 있다는 주장. Gas Town의 SKILL.md별 격리된 프롬프트도 같은 맥락.

5. Cross-Provider Context Handoff → 미래 전략

세션 중간에 모델을 바꾸는 기능. 비싼 작업은 Opus, 루틴은 Haiku, 코딩은 Sonnet — 이미 Gas Town에서 하고 있는 것을 세션 레벨에서도 할 수 있다는 의미.

6. 🔑 가장 큰 인사이트

"AI 에이전트 개발을 메인 잡으로" 라는 목표에서, 모델 API를 직접 호출하는 것보다 하네스 레이어를 만드는 사람이 더 오래 살아남는다. 모델은 commodity가 되지만, 실행 구조(하네스)는 경쟁 우위로 남는다.

Pi 스택을 직접 사용하든, OpenClaw 위에서 확장하든, 핵심은:

  • 모델 비종속
  • 컨텍스트 엔지니어링
  • 확장 가능한 도구 체계
  • 세션과 상태 관리

이 4가지를 소유한 사람이 AI 시대의 인프라 소유자.
