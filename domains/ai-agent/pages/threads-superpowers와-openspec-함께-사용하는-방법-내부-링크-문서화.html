요약

관련 키워드: [[OpenSpec]], [[Spec-Driven Development]], [[AI Agent Workflow]], [[TDD]], [[Documentation]]

write_dev.san의 글 핵심은 변경 크기에 따라 워크플로우를 분기하는 것입니다.

  • 큰 변경: superpowers로 브레인스토밍/계획/실행 후 openspec으로 사양 동기화
  • 중간 변경: openspec 표준 흐름(propose → apply → archive) 사용
  • 작은 변경: 바로 수정하되, 별도 delta spec 대신 main spec에 직접 반영하는 opsx-spec-patch 같은 보조 커맨드 사용

핵심 메시지는 이겁니다.

사양 유지 비용은 들지만, 프로젝트 중후반부로 갈수록 사양 없이 누적된 작은 변경들이 더 큰 토큰 낭비와 반복 시행착오를 만든다.

원문 구조 정리

1) 큰 구현/수정

대상:

  • 초기 구현
  • 큰 기능 추가
  • 기존 구현을 크게 변경하는 작업

추천 흐름:

  1. /superpowers:brainstorming
  2. /superpowers:write-plan
  3. /superpowers:execute-plan
  4. 이후 openspec으로 사양 동기화
    • /opsx:propose
    • /opsx:archive

해석

여기서는 superpowers가 멀티 에이전트 오케스트레이션, 심층 브레인스토밍, TDD, 동시 구현에 강하다고 봅니다.

반면 openspec은 항상 최신 사양을 유지하는 시스템 역할입니다.

즉,

  • 구현의 생산성/탐색/실행 = superpowers
  • 구현 결과를 공식 지식으로 굳히는 일 = openspec

2) 크진 않지만 사양이 필요한 구현

추천 흐름:

  • /opsx:propose → /opsx:apply → /opsx:archive

해석

이 경우는 superpowers 수준의 큰 계획 프로세스까지는 필요 없지만,

그래도 사양으로 남겨둘 가치가 있는 변경입니다.

즉, OpenSpec의 정규 변경 프로세스를 그대로 타는 구간입니다.

3) 아주 작은 구현/수정

추천 흐름:

  • 에이전트로 바로 수정
  • 이후 main spec에 빠르게 반영
  • 이를 위해 spec-patch 성격의 커맨드 사용

Threads 본문에서 연결한 내부 링크는 아래 gist입니다.

내부 링크 문서화 — OpenSpec Inline Spec Patch

gist 제목:

OpenSpec Inline Spec Patch — apply ad-hoc fixes directly to main specs

이 문서는 /opsx-spec-patch [component/spec-path] 형태의 보조 커맨드를 정의합니다.

목적은 이미 구현이 끝난 작은 수정을 별도 formal change 없이 기존 main spec에 직접 반영하는 것입니다.

이 커맨드가 전제하는 상황

gist 기준 전제는 아래와 같습니다.

  • 코드 구현은 이미 끝났고 테스트도 통과함
  • 변경이 기존 spec 범위 안에서 설명 가능함
    • 기존 컴포넌트 spec에 Requirement/Rule/Scenario 추가 정도로 정리 가능
  • 하나의 concern으로 표현 가능함
  • 여러 컴포넌트를 동시에 크게 건드리는 수준은 아님

즉, 작고 이미 끝난 변경을 사양에 반영하는 후처리 도구에 가깝습니다.

gist가 제시하는 절차

  1. 대화 컨텍스트에서 spec에 반영해야 할 내용을 식별
    • 새로 발견된 아키텍처 규칙/제약
    • 추가/변경된 동작
    • 새롭게 커버되는 시나리오
  1. $OPENSPEC/specs/ 아래에서 가장 관련 높은 component spec 찾기
    • 인자가 있으면 해당 spec 직접 사용
    • 없으면 후보를 보여주고 사용자와 확인
  1. 기존 spec 형식에 맞춰 patch 초안 작성
    • Requirement
    • Scenario
    • 필요 시 Rule
    • 특히 Rule에는 Rationale 포함
  1. 사용자 승인 받기
    • 어느 파일 어느 위치에 넣는지
    • patch 내용이 무엇인지
    • 수정 요청 반영
  1. 승인 후 spec file에 반영

gist의 중요한 제약

1. Rule에는 rationale이 꼭 있어야 함

특히 “하면 안 된다” 같은 금지성 규칙은 왜 금지하는지를 남겨야,

나중에 에이전트나 사람이 그 제약을 맥락 없이 오해하지 않습니다.

2. code와 spec은 함께 커밋

gist는 spec만 따로 커밋하는 것을 명시적으로 경계합니다.

이유는 코드-사양 연결 고리가 git history에서 끊기기 때문입니다.

3. 여러 컴포넌트에 걸치면 formal change로 가야 함

inline patch는 single spec file modification only라는 제한이 있습니다.

한 파일에서 끝나지 않으면 정식 change workflow로 올리라는 뜻입니다.

이 글의 실무적 의미

왜 이 분리가 유효한가

이 글은 사실상 아래 운영 원칙을 제안합니다.

  • 탐색이 큰 일은 계획/실행 도구를 적극 활용한다.
  • 기록이 중요한 일은 spec workflow를 탄다.
  • 너무 작은 일도 spec 반영만큼은 빼먹지 않는다.

즉, “모든 변경에 동일 프로세스”가 아니라,

변경 크기별로 비용 대비 최적화된 프로세스를 쓰자는 접근입니다.

특히 좋은 포인트

1. 작은 수정 누락이 만드는 컨텍스트 부채를 정확히 짚음

글에서 가장 좋은 포인트는 이 부분입니다.

작은 수정은 사양 반영을 건너뛰기 쉽지만,

이게 누적되면 에이전트는 이전 결정을 모르는 상태가 됩니다.

그러면:

  • 이미 결정된 방향을 다시 제안하고
  • 정책과 어긋난 수정이 나오고
  • 다시 과거 맥락을 설명해야 하고
  • 자료가 없으면 재조사/재분석 비용이 생깁니다.

이건 곧 컨텍스트 부채(context debt)입니다.

2. formal workflow와 ad-hoc patch의 경계가 명확함

아무 데나 patch를 쓰는 게 아니라,

  • single concern
  • single spec file
  • 이미 구현 완료

라는 제약을 두고 있습니다.

이 제약이 없으면 spec 체계가 금방 흐트러지는데,

gist는 그 선을 비교적 잘 그어둔 편입니다.

3. “사양은 최신 상태여야 한다”는 운영 철학이 분명함

openspec의 장점으로 main spec + delta spec 구조와,

구현 후 archive를 통해 main spec을 최신 상태로 만든다는 점을 강조합니다.

결국 이 글 전체는 다음 한 문장으로 요약됩니다.

구현 방식은 유연하게, 하지만 최종 사양은 항상 최신 상태로 유지하자.

/superpowers:write-plan

자비스 메모

이 글은 “사양 유지 비용 vs 사양 부재 비용”을 비교해서,

후자가 더 커지는 시점을 잘 짚은 운영 글입니다.

특히 에이전트 개발 프로젝트에서는 작은 수정이 쌓이면서 실제 구현과 문서가 어긋나기 쉬운데,

그 틈을 메우기 위한 lightweight spec sync 커맨드가 opsx-spec-patch라고 보면 됩니다.

다만 이 방식은 이미 구현이 끝난 변경을 문서화하는 후행 프로세스라서,

설계 검토가 먼저 필요한 변경까지 모두 여기로 보내면 spec 품질이 약해질 수 있습니다.

그래서 gist가 제한한 조건(single concern, single spec file, formal change 아님)을 지키는 게 중요합니다.
