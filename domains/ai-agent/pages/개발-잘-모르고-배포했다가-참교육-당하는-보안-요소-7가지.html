개발 잘 모르고 배포했다가 참교육 당하는 보안 요소 7가지

#실수결과
1시크릿을 깃헙에 커밋깃허브 돌아다니는 Bot들이 1초 만에 수집 → 3시간 만에 AWS 요금 800만원
2시크릿을 프론트 코드에 넣음브라우저에서 F12 열면 전 세계 공개
3/admin 페이지, 인증 없이 URL만 알면 입장누구나 관리자 페이지 진입
4정수 PK를 URL에 그대로 노출id 1씩 올리는 매크로로 전 게시물 긁기 + 댓글 도배 (UUID 쓰세요)
5rate limit 없는 문자인증 API새벽에 요금 폭탄
6/api/user?id=1 요청id만 바꿔 요청하면 남의 정보 조회 (인증 체크 없음)
7DB 포트 3306, 인터넷에 오픈전세계 봇들이 줄 서서 비번 두드리기 시작

댓글 스레드 (Reply Thread — 작성자 추가 내용)

추가)

  1. 라이브러리 보안 업데이트 방치 → React2Shell 같은 게 터지면 서버 통째로 뚫림
  2. 비밀번호를 평문으로 저장 → DB 털리면 전 회원 이메일 + 비번 그대로 → 해당 회원의 다른 서비스 계정들 도미노로 털림 (크리덴셜 스터핑)
  3. API 키 발급 시 모든 권한 부여 → 키 털리면 피해도 무제한

정정)

4번 "정수 PK 노출"은 참교육이 아니라 권고 수준이 맞습니다. 제 실수예요.

정수 PK 자체는 취약점이 아니고, 인증 체크만 제대로 하면 문제없습니다.

인증 체크 잘 하면서 정수 ID 쓰시는 분들 뜨끔하게 해드렸다면 죄송합니다.

댓글 (Other Users)

  • 보안 참 중요하지! 근데 요즘 클로드나 코덱스 모두 보안 관련해서 시크릿이나 민감정보는 git pull이나 소스코드에 절대 쓰지 마라 하고, 보안 취약점 조사해서 보고해 하면 잘 찾아주는 듯! 바이브코딩이 문제가 아니고 정말 보안이 문제야.
  • 하나같이 꺅 소리 나오는 모음집이네요.
  • private해도 bot들이 봐요? → private은 bot들이 못 봅니다. (작성자 답변)
  • 참고할게요. 전세계 공용 API가 되지 않도록.
  • 깃에 키 올리기 전에 pre-commit hook으로 패턴 한번 걸러두는 게 제일 싸요.
  • 정수 PK vs UUID + 댓글 도배 상세 설명:

4번에서 정수 PK 대신 UUID(랜덤 생성 ID)를 쓰라는 이유 — 쉽게 예측·긁기 불가하도록.

댓글 도배 관련: '댓글 등록' 버튼을 누르면 브라우저는 서버에 최소한 '어떤 게시물'에 댓글을 달았는지 넘긴다. '이전/다음 게시물' 주소를 쉽게 예상할 수 있으면 정상 접근 과정을 무시하고 그냥 쏴버릴 수 있다.

  POST api/.../comments
  { article_id: {1}, comment_text: "스팸내용" }

→ id 부분만 바꿔가며 반복 전송하면 전 게시물 댓글 도배.
