본문 (Main Post)

🚨 AI 에이전트도 사람처럼 잠자는 동안 기억을 정리하고 실수를 고치는 시대. 앤트로픽이 공개한 "Dreaming"은 AI가 지난 작업을 되짚고 잘못된 기억을 수정하는 방식이다. 포켓몬 게임에서 막힌 문제를 해결했고, 기업 문서 35만 개를 연결해 답변 정확도를 높였다. 🧵

댓글 스레드 (Reply Thread, 작성자 @choi.openai 1/ ~ 9/)

  1. 1/ 구조: 사람은 해마가 경험을 바로 기록하고, 수면 중 되짚어 오래 남길 지식만 신피질로 옮긴다. 에이전트 기억도 같은 분업이 가능하다. 일하는 동안 대화 기록과 메모를 남기고, 세션 사이에 다시 읽어 실수를 고친다. Letta와 UC 버클리의 sleep-time compute가 출발점이다. 기억은 4층이다: 대화 기록, Claude가 쓴 메모, 위키 같은 정리본, 매 세션 시작 시 주입하는 맥락.
  2. 2/ 기억은 예측: 규칙을 적는 일은 그 패턴이 다시 필요하리라는 예측이다. CL-Bench 데이터베이스 과제에서 모델별로 학습 고리의 완성도가 달랐다. Sonnet 4.6은 추측만 흩어 놓았고, Opus 4.7은 확인/미확인을 구분했고, Opus 5부터 규칙+근거+함정 경고로 고리를 닫았다. 작성자는 점수를 기억 없음 0.564 → 기억 사용 0.828(Opus 5), Opus 5.5 0.838, Sonnet 5.5 0.833으로 인용했다.
  3. 3/ 무엇을 기억할지: 포켓몬 레드 비교(위 표). Fable 5는 화면에 항상 보이는 돈/위치는 적지 않고, 현재 목표, 체육관 공략 계획, 직접 시험한 규칙만 적었다. 예: 잉어킹에게 몬스터볼 7개가 연속 실패하자 "3번 넘게 실패하면 던지는 타이밍을 바꿔라"를 남겼다.
  4. 4/ 지시 방식: 기억이 무엇을 위한 것인지만 알리고 쓰는 방법은 모델에 맡기는 쪽이 낫다. "실패만 기록" 규칙을 걸자 Opus 5는 기억으로 얻던 이득에서 0.234가 줄었다. 반대로 오래된 모델은 지시가 도움이 됐다. Sonnet 4.6은 "답하기 전에 기억을 읽고 가설을 직접 시험하라"를 시키자 0.330 → 0.641로 거의 2배가 됐다. Sonnet 5는 지시 없이 10번 중 9번 먼저 기억을 읽었다.
  5. 5/ 달맞이산 사례: Claude가 포켓몬센터 위치를 동쪽이라 잘못 적고 "달맞이산 완료"라고 메모했다. 그대로 걷다 낭떠러지로 세 번 떨어졌고, 결국 이전 마을로 돌아가 끝났다. dreaming으로 메모를 대화 기록과 대조해 오류를 고치자, 고친 메모로 시작한 실행은 동굴로 돌아가 1,935번째 행동에서 블루시티(원문 표기 Cerulean City)에 도착했다.
  6. 6/ 위키: 주제별로 지식을 모으고 다른 노트와 링크로 잇는 문서 묶음. Stainless 문서 35만 개, 4.2억 토큰, 질문 25개, Opus 5 에이전트 128세션. 위키만 13% → 48%, 검색+위키 54% → 61%(검색만 53%), 질문당 약 2만 토큰 절감. 작성자는 4월에 정리한 카파시 LLM 위키와 같은 방향을 앤트로픽이 실험 수치로 보여준 셈이라고 평가했다.
  7. 7/ 위키가 항상 이득은 아님: 합병 문항 24개(다문서 결합)에서 위키 87% vs 검색 73%. 문서 하나에서 바로 검색되는 법률 브리프 과제는 차이가 없었고, 한 과제에서는 위키가 원본 문서보다 1.77배 커졌다. 앤트로픽은 이를 보르헤스의 제국만 한 지도에 빗대 "아무것도 요약하지 못한 위키"라고 적었다.
  8. 8/ 위키 설계: 인수 계약서 브리프 과제에서 에이전트 여러 개가 표 하나에 동시에 쓰다 서로 덮어써 57개 중 41개(72%)만 남았다. Claude가 실패를 되짚어 위키 작성 지침을 직접 고쳤다(계약서당 에이전트 1개, 페이지 1개, 조건은 요약 없이 원문 그대로). 결과 57개 전부 보존. 매 세션 주입 기억은 작게 유지해야 하며, Claude Code auto memory는 MEMORY.md 첫 200줄/25KB만 읽는다.
  9. 9/ 빈틈 메우기: 두 번째 dreaming에서 존재하지 않는 페이지를 가리키던 링크 9개를 실제 페이지로 고치고, 색인 페이지 포함 새 페이지 3개를 추가했다. 5월 Claude Managed Agents에 기능으로 먼저 들어왔고, 6월 OpenAI ChatGPT와 10월 Cognition Devin도 같은 이름의 기억 정리 기능을 냈다고 한다(작성자 서술, 원문 본문에는 없음). 작성자 전망: 에이전트 경쟁은 얼마나 많이 기억하느냐보다 무엇을 버리고 언제 다시 확인하느냐에서 갈릴 것이다.

작성자의 과거 글 2개가 스레드에 같이 붙어 있다(본 포스트의 일부가 아니라 참조용).

  • 2026-04-05: 카파시 LLM 위키가 하루 만에 270만 회를 넘겼다는 소개. RAG처럼 매번 찾는 대신 LLM이 원문을 요약, 교차 검증, 링크 연결해 마크다운 위키를 누적하는 구조.
  • 2026-05-07: Claude Managed Agents에 Dreaming과 Outcomes loop 추가 소식. 초기의 잘못된 패턴이 굳어질 우려도 언급.

원문이 인정한 한계와 열린 질문

  • 기억 생성 시점: 작업 중 기록은 주의를 빼앗고, dreaming은 백그라운드에서 하지만 결과를 즉시 쓸 수 없다.
  • 최신성 유지: 틀린 규칙이나 환경 변화에 따른 drift가 생긴다. dreaming은 연산 비용이 든다. 모든 기억을 계속 점검하기보다 변하기 쉬운 정보에 집중하거나 접근 빈도에 따라 주기를 조정해야 한다.
  • 대안: transcript 검색을 기억의 기초로 삼는 방법. 위키와 검색 결합이 효과적일 수 있으나, 위키는 오류와 hallucination이 쌓이지 않게 연산으로 유지해야 한다.
  • 시작용 자료: 원문 하단에 dreaming과 knowledge wiki cookbook 링크가 있다.

활용 메모 (우리 환경 연결점, 참고용)

  • Claude Code auto memory가 MEMORY.md 첫 200줄/25KB만 읽는다는 한도가 원문에서 확인됐다. 상시 주입 층(우리 SOUL.md, MEMORY 등)은 작게 유지하고 세부는 링크로 내리는 설계와 같은 방향이다.
  • 위키가 이득이 되는 조건은 다문서 결합과 판단/계산이 필요한 질문이다. 단일 문서 검색으로 풀리는 과제는 위키 이득이 없고, 오히려 위키가 원본보다 커질 수 있다.
