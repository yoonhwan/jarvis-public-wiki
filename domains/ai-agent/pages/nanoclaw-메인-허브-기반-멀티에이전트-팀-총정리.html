NanoClaw 메인 허브 기반 멀티에이전트 팀 총정리

목적: NanoClaw를 메인 허브로 두고, Slack을 중심 채널로 사용하는 멀티에이전트 코딩/리서치 팀을 설계·운용하기 위한 전체 컨텍스트 정리.

1. 전체 그림

  • 중앙 허브: NanoClaw 호스트(Node.js 프로세스)
    • Slack/텔레그램/Web 등 채널과 연결
    • 태스크/상태/세션 관리
    • 오케스트레이터 에이전트(모차르트)가 여기서 동작
  • 분산 에이전트: 컨테이너 단위로 배포되는 역할 에이전트들
    • 브레드(프론트), 로드니(서버), 알렉스(아키텍트), 데빌스(반론가) 등
    • 각 에이전트는 Claude Agent SDK/코딩툴 기반으로 작업 수행
    • 컨테이너는 로컬/클라우드/온프레 어디서나 실행 가능
  • Slack 중심
    • 사람 ↔ 허브(모차르트) ↔ 역할 에이전트 간 모든 상호작용이 Slack에서 보이고, 제어된다.

2. 에이전트 정의 철학

에이전트 = 역할(Role) + 스킬(Skills) + 기억(Memory) + 채널(Channel)

  • 역할(Role)
    • 이 에이전트가 책임지는 도메인과 작업 범위
    • 예: 팀 리더, 아키텍트, 프론트 개발, 백엔드 개발, 악마의 반론가
  • 스킬(Skills)
    • 에이전트가 호출할 수 있는 도구/연결 집합
    • 예: Claude Code/Agent SDK, Git, CI/CD, 리서치, Slack 메시지, 캘린더, 파일 I/O 등
  • 기억(Memory)
    • 세션/작업 로그, 결정 기록, 도메인 노하우
    • NanoClaw: 에이전트 컨테이너 내 디렉토리 (instructions, notes, artifacts 등)
    • 별도 거대한 메모리 시스템 설계 없이, 기본 워크스페이스 + Slack/채널 맥락을 활용
  • 채널(Channel)
    • 사람이 에이전트에게 말 거는 창구, 결과를 받는 인박스
    • Slack을 1차 채널로 사용 (DM/채널/쓰레드)

핵심: "에이전트 영속성/메모리"를 따로 무겁게 설계하지 않고, NanoClaw의 기본 워크스페이스 + Slack의 대화/파일/쓰레드 맥락을 통해 자연스럽게 진화하는 팀원으로 만든다.

3. 3계층 아키텍처

1) UI/채널 층

  • Slack, Telegram, Web UI 등
  • 사람과 에이전트 팀이 상호작용하는 인터페이스

2) 허브/오케스트레이터 층

  • NanoClaw 호스트 + 모차르트 에이전트
  • 역할:
    • 사용자 메시지를 수신하고 태스크로 변환
    • 어떤 역할 에이전트에게 태스크를 줄지 결정
    • 에이전트 간 위임/병렬 작업을 조율
    • Slack 이벤트/훅 기반 상태 업데이트 및 후속 액션 결정

3) 작업자(역할 에이전트) 층

  • 브레드(프론트), 로드니(서버), 알렉스(아키텍트), 데빌스(반론가) 등
  • 내부에서 Claude Code/Agent SDK 및 기타 스킬을 사용해 실제 코딩/리서치/리뷰를 수행
  • 각 에이전트는 독립 컨테이너로 실행, 환경/권한/디렉토리 분리

4. 역할 에이전트 팀 구성

4.1 공통 스펙

각 역할 에이전트가 공통적으로 가지는 요소:

  • Provider / Model
    • 예: Anthropic Claude (Opus, Sonnet, Claude Code 등)
  • Skills 번들 (예시)
    • 코드 편집/리팩터링/테스트 스킬
    • Git/PR/브랜치 관리 스킬
    • 웹/문서 리서치 스킬
    • Slack 메시지 전송/요약 스킬
    • 파일/디렉토리 I/O 스킬
  • Workspace / Memory
    • instructions.md (역할/톤/원칙)
    • notes/ 혹은 memory/ 디렉토리 (세션 요약, ADR, 회고)
    • artifacts/ 디렉토리 (diff, 리포트, 로그, 문서)
  • 채널 연결 정보
    • 주로 사용하는 Slack 채널/멘션/쓰레드 규칙

4.2 역할 예시

  • 모차르트 (팀리더 / 오케스트레이터)
    • 책임: 요청 이해, 태스크 분해, 역할 에이전트에게 위임, 결과 합성
    • 스킬: 태스크/상태 관리, Slack 입출력, 다른 에이전트 호출/조율
  • 알렉스 (아키텍트)
    • 책임: 시스템/모듈 설계, 인터페이스, ADR/문서화
    • 스킬: 설계/문서 작성, 리서치, 코드 구조 리뷰
  • 브레드 (프론트 개발)
    • 책임: 프론트엔드/클라이언트 코드 구현, UI/UX 관련 작업
    • 스킬: JS/TS/React 등 프론트 스택, Git, 브라우저/빌드 도구
  • 로드니 (서버 개발)
    • 책임: 백엔드/API/DB/인프라 코드 구현, 배포/운영 보조
    • 스킬: 서버 언어, DB, IaC, 모니터링/로그 관련 스킬
  • 데빌스 (악마의 반론가)
    • 책임: 설계/코드/결정에 대한 리스크/대안/가정 검증
    • 스킬: 리뷰 템플릿, 체크리스트, 리스크 분석/프리모텀

6. 통신 프로토콜 (심플 JSON)

6.1 공통 메시지 스키마

허브 ↔ 에이전트, Slack 훅 ↔ 허브 모두에 공통으로 사용하는 최소 JSON 구조:

{
  "task_id": "T-123",
  "from": "MOZART",
  "to": "BREAD",
  "status": "pending",
  "summary": "로그인 UI 구현 요청",
  "artifacts": [
    {
      "type": "link",
      "value": "https://github.com/org/repo/pull/456"
    },
    {
      "type": "file",
      "value": "artifacts/T-123/diff.patch"
    }
  ],
  "meta": {
    "channel": "slack",
    "thread_ts": "1710761234.56789",
    "requested_by": "@user"
  }
}
  • 필드 설명
    • task_id: 태스크 고유 ID (예: "T-123")
    • from: 발신 주체 (MOZART, BREAD 등)
    • to: 수신 에이전트
    • status: pending / working / done / needs-input / failed
    • summary: 짧은 설명 또는 명령
    • artifacts: 링크·파일·텍스트 등 결과물 위치
    • meta: Slack/채널 관련 메타데이터

6.2 상태 머신

  • 기본 상태 흐름:
    • pending → working → done
  • 보조 상태:
    • needs-input: 추가 정보/결정 필요
    • blocked: 외부 의존성 때문에 진행 불가
    • failed: 에러로 실패

허브(모차르트)가 이 상태 머신을 유지하고, 에이전트/Slack는 이벤트 트리거 역할만 한다.

7. Slack 중심 워크플로

7.1 사람 관점

  1. 유저가 Slack에서 모차르트를 멘션:
    • 예: "@mozart 새 로그인 페이지 UI 만들고 기존 로직에 연결해줘"
  2. 허브(모차르트)가 메시지를 받아 태스크 생성(T-123) 후, 담당 에이전트(브레드)에 위임
  3. 브레드가 NanoClaw 컨테이너 내부에서 코드/테스트/PR 작업 수행
  4. 브레드가 완료 보고를 허브에 전송 → 허브는 Slack 쓰레드에 결과 요약/링크 게시
  5. 유저가 Slack에서 승인/수정 요청 → 허브가 다시 이벤트를 받아 후속 태스크 생성 또는 다른 에이전트에 위임

7.2 시퀀스 다이어그램 (모차르트 ↔ 브레드)

sequenceDiagram
  participant U as User
  participant S as Slack
  participant M as 모차르트 허브
  participant B as 브레드 에이전트

  U->>S: "새 로그인 UI 만들어줘"
  S->>M: 메시지 이벤트(Webhook/Socket)

  M->>M: T-123 태스크 생성<br/>owner = 브레드
  M->>B: T-123 작업 요청<br/>요구사항/맥락 전달

  B->>B: 코드 작성/테스트/아티팩트 생성
  B->>M: T-123 완료 + 결과 요약/링크

  M->>S: T-123 결과 요약 메시지<br/>(쓰레드로 전송)
  S->>U: 결과 표시

  S->>M: (옵션) 유저 피드백/승인 이벤트
  M->>M: 후속 태스크 생성 또는 워크플로 종료

8. NanoClaw를 메인 허브로 쓰는 이유

  • 에이전트 = 컨테이너
    • 각 역할 에이전트를 컨테이너 단위로 분리해, 코드/데이터/권한을 깔끔하게 격리할 수 있음.
  • 1 허브 N 에이전트 구조가 기본
    • 단일 NanoClaw 호스트가 Slack 이벤트 수신, 태스크 생성/할당, 컨테이너 에이전트 호출을 모두 담당하는 구조가 공식 아키텍처에 부합.
  • Agent Swarm / 멀티에이전트 지원
    • Claude Agent SDK 기반으로 여러 에이전트가 협업하는 Swarm 패턴이 이미 전제되어 있어, 역할 에이전트 팀 구성에 자연스럽게 매핑.
  • 보안/운영 이점
    • 컨테이너별로 File/Network/Env를 최소 권한으로 세팅 가능해, 서버/인프라 담당 에이전트도 상대적으로 안전하게 운용.

9. 최소 실행 버전(MVP) 제안

  1. 에이전트 최소 구성
    • 모차르트(허브 내 팀리더)
    • 브레드(프론트/코딩)
  1. 채널
    • Slack 하나만 우선 연결
  1. 기능 범위
    • Slack에서 모차르트에게 기능 요청
    • 모차르트가 T-XXX 태스크 생성 후 브레드에게 위임
    • 브레드가 코드 작성/결과 정리 후 허브에 보고
    • 허브가 Slack 쓰레드에 결과 요약/링크 게시
  1. 그 다음 확장
    • 로드니(서버), 알렉스(아키텍트), 데빌스(반론가) 단계적 추가
    • skill-native의 21 크루 스킬을 역할별 스킬 번들로 재맵핑
    • 필요시 Redis/Kafka 등 별도 버스를 붙여 대규모 스케일 대응

이 문서는 NanoClaw를 메인 허브로 사용하는 멀티에이전트 팀 구조의 전체 컨텍스트를 담은 기준 문서로 쓰면 된다.
