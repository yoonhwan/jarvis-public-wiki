Slack 기반 멀티에이전트 코딩 팀 허브 설계서 (OpenClaw / NanoClaw)

목표: 허브 한 대에서 여러 "역할 에이전트"를 운용하고, 각 에이전트는 클라우드/온프레 환경에 맞게 배포된 실제 작업자로 동작하게 만들기. Slack을 중심 채널로 써서, 사람 + 에이전트 팀이 같이 일하는 구조.

1. 기본 철학

1.1 에이전트 정의

에이전트 = 역할 + 스킬 + 기억 + 채널

  • 역할(Role)
    • 이 에이전트가 담당하는 책임과 전문 영역
    • 예: 팀리더, 아키텍트, 프론트엔드, 백엔드, 악마의 반론가
  • 스킬(Skills)
    • 에이전트가 사용할 수 있는 도구 세트
    • 예: 코딩(Claude Code/Agent SDK), Git, 빌드/테스트, 리서치, Slack 메시지, 캘린더
  • 기억(Memory)
    • 에이전트가 축적해 가는 맥락/노하우/결정 기록
    • OpenClaw: 에이전트 워크스페이스 디렉토리의 메모리 파일들
    • NanoClaw: 컨테이너 내부 디렉토리(세션 로그, instructions 등)
  • 채널(Channel)
    • 사람 및 다른 시스템과 연결되는 입출력 인터페이스
    • Slack / 텔레그램 / 웹 / CLI 등

핵심: 에이전트의 영속성을 위해 별도의 거대한 메모리 시스템을 새로 설계하지 않고, 프레임워크(OpenClaw/NanoClaw/Claude 에이전트)의 기본 메모리 + Slack/채널 맥락을 그대로 활용한다.

2. 3계층 아키텍처

2.1 계층 구조

  1. 사용자 인터페이스 층 (UI/채널)
    • Slack, Telegram, Web 등
    • 사람과 에이전트 팀이 상호작용하는 창구
    • 모든 알림·요청·결과가 여기에 드러난다
  1. 오케스트레이터 층 (허브 + 팀리더 에이전트)
    • NanoClaw / OpenClaw 허브 + "모차르트" 에이전트
    • 역할:
      • 사용자 요청 → 태스크로 변환
      • 어떤 역할 에이전트에 위임할지 결정
      • 에이전트 결과를 합성해 다시 사용자에게 응답
      • Slack 이벤트/훅을 받아 상태머신을 돌리는 중앙 컨트롤러
  1. 작업자 층 (역할 에이전트들)
    • 알렉스(아키텍트), 브레드(프론트), 로드니(서버), 데빌스(악마의 반론가) 등
    • 내부에서 코딩툴/모델/스킬을 실제로 실행하는 "개별 작업자"
    • 각 에이전트는 자기 워크스페이스와 모델, 스킬 번들을 가진다

3. 에이전트 팀 구성

3.1 공통 에이전트 스펙

각 에이전트는 다음을 최소 단위로 가진다:

  • Provider / Model
    • 예: Anthropic Claude (Opus, Sonnet, Claude Code 등)
  • Skills 번들
    • 코딩: 프로젝트 코드 편집/리팩터링/테스트
    • Git: PR, 브랜치, 커밋 관리
    • 리서치: 웹/문서 탐색
    • Slack: 메시지 전송/요약
    • 기타 필요 도메인 스킬
  • Workspace / Memory
    • 역할 정의 파일 (instructions.md, AGENT.md 등)
    • memory/ 디렉토리(세션 요약, 결정, 히스토리)
    • artifacts/ 디렉토리(리포트, diff, 로그, 문서)
  • 채널 연결 정보
    • 어떤 Slack 채널/쓰레드/멘션을 주로 사용하는지
    • 기타 메신저/웹 훅 엔드포인트

3.2 역할별 에이전트 예시

  • 모차르트 (팀리더 / 오케스트레이터)
    • 책임: 사람 요청을 해석해 태스크 정의, 적절한 작업자 에이전트에게 위임, 결과 합성 및 최종 응답
    • 스킬: 태스크/상태 관리, Slack 요약/응답, 다른 에이전트 호출/조율
  • 알렉스 (아키텍트)
    • 책임: 시스템 설계, 모듈 경계, 인터페이스, ADR 작성
    • 스킬: 설계/문서화, 리서치, 코드 구조 리뷰
  • 브레드 (클라이언트 코딩)
    • 책임: 프론트/클라이언트 코드 구현 및 리팩터링
    • 스킬: JS/TS/React 등 클라 코드, Git, 브라우저 관련 도구
  • 로드니 (서버 코딩)
    • 책임: 백엔드/API/DB/인프라 코드 구현
    • 스킬: 서버 언어, DB, 인프라 IaC, 배포/모니터링 스킬
  • 데빌스 (악마의 반론가)
    • 책임: 설계/코드/결정에 대해 리스크/대안/가정 검증
    • 스킬: 리뷰 템플릿, 체크리스트, 리스크 모델링

4.2 배포 모델

  • 중앙 허브 1대 (또는 클러스터)
    • NanoClaw / OpenClaw 게이트웨이
    • Slack/텔레그램/웹 등 모든 채널과 연결
    • 태스크/상태 관리 및 오케스트레이션 담당
  • 에이전트 컨테이너들
    • 브레드/로드니/알렉스/데빌스 각자의 컨테이너
    • 로컬, 클라우드, 온프레, 엣지 등 원하는 환경에 배포
    • 허브와는 RPC/큐/HTTP/메시지 버스로 통신

5. 통신 프로토콜 (심플 & 일반화)

5.1 기본 메시지 스키마

에이전트 간, 허브 ↔ 에이전트, Slack 훅 모두에 공통으로 쓰는 최소 포맷:

{
  "task_id": "T-123",
  "from": "MOZART",
  "to": "BREAD",
  "status": "pending",
  "summary": "로그인 UI 구현 요청",
  "artifacts": [
    {
      "type": "link",
      "value": "https://github.com/org/repo/pull/456"
    },
    {
      "type": "file",
      "value": "artifacts/T-123/diff.patch"
    }
  ],
  "meta": {
    "channel": "slack",
    "thread_ts": "1710761234.56789",
    "requested_by": "@user"
  }
}

이 한 타입으로:

  • 허브 → 에이전트: 작업 지시
  • 에이전트 → 허브: 진행 상황/완료 보고
  • Slack 훅 → 허브: 유저 피드백/승인 이벤트
  • 허브 → Slack: 요약 메시지/결과 보고

까지 모두 커버한다.

5.2 상태 머신 (태스크 수준)

  • 상태:
    • pending → working → done
    • 보조 상태: needs-input, blocked, failed
  • 전이 예시:
    • pending → (에이전트 할당) → working
    • working → (작업 완료) → done
    • working → (추가 정보 필요) → needs-input
    • needs-input → (유저 응답) → working
    • working → (에러) → failed

허브(모차르트)가 이 상태 머신을 관리하고, 에이전트와 Slack 이벤트는 상태 변화의 트리거 역할만 한다.

6. Slack 중심 워크플로

6.1 Slack에서 보는 관점

  • 유저는 그냥 Slack에서:
    • 채널/DM에서 "@mozart 이번 로그인 기능 정리해줘" 같은 메시지를 보냄
  • 허브:
    • 이 메시지를 이벤트로 받아 태스크 생성 → 적절한 에이전트(BREAD/RODNEY 등)에 할당
  • 작업자 에이전트:
    • 내부에서 코딩/테스트/리뷰 수행
    • 완료/중간 결과를 Slack 쓰레드에 다시 메시지로 보고
  • 허브:
    • Slack 훅으로 들어온 메시지/리액션/버튼을 해석해 태스크 상태를 업데이트하고,
    • 필요하면 다음 에이전트에게 위임 또는 워크플로 종료

6.2 모차르트 ↔ 브레드 1사이클 시퀀스

sequenceDiagram

  participant S as Slack
  participant M as 모차르트 허브
  participant B as 브레드 에이전트

  U->>S: "새 로그인 UI 만들어줘"
  S->>M: 메시지 이벤트(Webhook/Socket)

  M->>M: T-123 태스크 생성<br/>owner = 브레드
  M->>B: T-123 작업 요청<br/>요구사항/맥락 전달

  B->>B: 코드 작성/테스트/아티팩트 생성
  B->>M: T-123 완료 + 결과 요약/링크

  M->>S: T-123 결과 요약 메시지<br/>(쓰레드로 전송)
  S->>U: 결과 표시

  S->>M: (옵션) 유저 피드백/승인 이벤트
  M->>M: 후속 태스크 생성 또는 워크플로 종료

7. OpenClaw vs NanoClaw 관점

7.1 OpenClaw

  • 기본 철학: Gateway(허브) 1개(또는 클러스터) + 그 안에 여러 에이전트 워크스페이스
  • 장점:
    • 메신저/툴 연동이 풍부하고, 로컬 퍼스트 개인 비서에 최적
    • 에이전트별 워크스페이스·메모리 관리가 이미 잘 정의
  • 한계:
    • 각 에이전트를 완전히 다른 서버/리전에 "서비스"로 뿌려놓고 허브가 원격 호출하는 모델은, 추가 설계가 필요

7.2 NanoClaw

  • 기본 철학: 각 에이전트 = 컨테이너, 허브는 이를 스케줄/제어
  • 장점:
    • 컨테이너만 올릴 수 있는 환경이라면 어디든 에이전트 배포 가능
    • 권한/리소스/네트워크를 에이전트별로 강하게 격리
  • 자연스러운 패턴:
    • 중앙 허브 1대
    • 에이전트 컨테이너는 클라우드/온프레/엣지 등 원하는 곳에 배포
    • 허브가 Slack/채널과 연결된 "중앙 관제탑"

이 기획서는 두 쪽 모두에 적용 가능한 상위 추상화고, 실제 구현에서 OpenClaw/NanoClaw에 맞게 adapter만 바꾸면 된다.

8. 최소 실행 가능한 버전 (MVP)

  1. 에이전트 2개부터 시작
    • 모차르트(팀리더)
    • 브레드(클라이언트/코딩)
  1. 채널 1개
    • Slack만 연결
  1. 통신 포맷
    • 위에 정의한 JSON 스키마 한 종류만 사용
  1. 동작 범위
    • 모차르트가 Slack에서 요구사항 수신
    • 브레드에게 작업 위임
    • 브레드가 코드/결과 정리 후 Slack에 보고
    • 모차르트가 그걸 받아 최종 메시지로 정리

이게 안정적으로 돌아가면:

  • 로드니(서버), 알렉스(아키텍트), 데빌스(반론가) 추가
  • skill-native의 21 크루 스킬을 역할별 스킬 번들로 재맵핑
  • 필요시 Redis/Kafka 같은 버스로 확장

9. 요약 키 포인트

  • "에이전트 영속성/메모리"를 새로 발명하지 말고, OpenClaw/NanoClaw/Claude 에이전트의 기본 워크스페이스 + Slack 맥락을 그대로 활용한다.
  • 에이전트 = 역할 + 스킬 번들 + 워크스페이스 + 채널로만 정의하고, 코딩툴/모델은 내부 구현 디테일로 본다.
  • 허브 1대(모차르트)가 Slack과 통신하고, 분산된 작업자 에이전트(브레드/로드니/알렉스/데빌스)를 오케스트레이션한다.
  • 통신은 task_id/from/to/status/summary/artifacts/meta 정도의 심플한 JSON으로 통일해서, Slack 훅/에이전트 간 위임/상태 관리에 모두 재사용한다.
